生产环境 CI/Release 用户通过 SSH 免密执行 psql 的配置方案

maiaimei 2026/11/15 PostgreSQL

# 结论先行

可以，而且这是生产环境中 CI/CD 场景的标准做法。 但关键在于用对认证方式，而不是简单地写 trust。

# 一、架构与连接路径分析

CI/Release 服务器
    │
    ├── SSH ──▶ 数据库服务器（已通过 SSH Key 认证，身份可信）
    │
    └── 本地执行 psql（Unix socket 或 localhost TCP）
1
2
3
4
5

既然已经通过了 SSH 认证，说明操作系统层面已经完成了身份验证。此时 psql 的认证应当复用这层信任，而不是再要求一次数据库密码。

# 二、推荐方案对比

方案 认证方式 安全性 运维复杂度 推荐度
方案 A：local + peer peer ⭐⭐⭐⭐⭐ 低 ⭐⭐⭐⭐⭐ 首选
方案 B：local + ident ident ⭐⭐⭐⭐ 中 ⭐⭐⭐⭐
方案 C：local + trust trust ⭐⭐ 最低 ⭐⭐（仅限隔离环境）
方案 D：.pgpass 文件 scram-sha-256 ⭐⭐⭐⭐ 中 ⭐⭐⭐（备选）

# 三、方案 A（推荐）：peer 认证 —— 最优雅的做法

# 原理

peer 认证利用 操作系统用户名 与 PostgreSQL 用户名 的一致性来完成认证。当 CI 用户通过 SSH 登录到数据库服务器后，OS 层面已经确认了身份；psql 通过 Unix socket 连接时，PostgreSQL 通过 getsockopt() 获取 OS 用户名，直接匹配数据库用户，无需密码。

# 前提条件

  1. CI/Release 在数据库服务器上有一个 OS 用户（如 ci_runner）
  2. PostgreSQL 中存在同名数据库用户（如 ci_runner），或通过 pg_ident.conf 做用户名映射

# 配置步骤

# 1️⃣ 创建 OS 用户（数据库服务器上）

useradd -m -s /bin/bash ci_runner
1

# 2️⃣ 创建 PostgreSQL 用户（数据库内）

CREATE USER ci_runner;
GRANT CONNECT ON DATABASE mydb TO ci_runner;
-- 按需授予权限
1
2
3

# 3️⃣ 配置 pg_hba.conf

# CI/CD 本地免密（peer 认证，复用 SSH 身份）
local   all   ci_runner   peer
1
2

# 4️⃣ 重载配置

SELECT pg_reload_conf();
1

# 5️⃣ 验证

# 以 ci_runner 身份 SSH 登录后
sudo -u ci_runner psql -d mydb -c 'SELECT current_user;'
# 无需密码，直接执行
1
2
3

# 如果 OS 用户名 ≠ 数据库用户名

使用 pg_ident.conf 做映射：

# pg_ident.conf
# MAPNAME     OS-USERNAME     PG-USERNAME
ci_map       ci_runner       deploy_user
ci_map       release_user    deploy_user
# pg_hba.conf
local   all   deploy_user   peer map=ci_map

# 四、方案 C（不推荐但需了解）：trust 认证

# 为什么通常不推荐

trust 意味着完全跳过身份验证。任何能连接到 Unix socket 的本地进程都可以直接登录，不验证 OS 身份。

# 仅限以下场景使用

  • 数据库服务器物理隔离，且本地无其他不可信进程
  • 容器化环境，数据库容器与 CI 容器严格隔离
  • 临时维护窗口

# 配置

local   all   ci_runner   trust
1

# 风险说明

如果数据库服务器上还存在其他应用用户或进程，它们也能以 ci_runner 身份直接连接数据库，无需任何凭证。

# 五、方案 D（备选）：.pgpass 文件

如果因运维限制无法使用 peer，可以用密码文件实现"免交互输入"：

# ~ci_runner/.pgpass
localhost:5432:mydb:ci_runner:StrongPassword123!
chmod 600 ~ci_runner/.pgpass
chown ci_runner:ci_runner ~ci_runner/.pgpass
# pg_hba.conf
host    mydb   ci_runner   127.0.0.1/32   scram-sha-256
host    mydb   ci_runner   ::1/128        scram-sha-256
1

此时 psql 自动读取 .pgpass，用户无需手动输入密码。

✅ 优点：审计友好（每次连接有完整认证日志）

❌ 缺点：密码文件需妥善管理，轮换密码时需同步更新

# 六、生产环境最佳实践总结

┌─────────────────────────────────────────────────────────────┐
│                    推荐配置矩阵                              │
├──────────────┬──────────────────┬───────────────────────────┤
│ 连接来源      │ pg_hba.conf 规则  │ 说明                      │
├──────────────┼──────────────────┼───────────────────────────┤
│ CI/Release   │ local all        │ peer 认证，复用 SSH 身份   │
│ (SSH 登录后) │ ci_user peer     │ 最安全、最简洁             │

│ 应用服务器    │ host mydb        │ scram-sha-256 + 密码       │
│ (远程 TCP)   │ app_user ip/mask │ 强制密码认证               │

# 核心原则

原则 说明
本地复用 OS 身份 SSH 已认证 → peer 认证，避免双重密码管理
远程强制密码 任何 TCP 远程连接 → scram-sha-256
最小权限 CI 用户只授予必要的 CONNECT + 迁移/发布所需权限
禁止 trust + host trust 只可用于 local 且需严格限定用户
审计日志 配合 log_connections = on 记录所有 CI 连接

# 七、快速检查清单

  • [ ] pg_hba.conf 中 CI 用户使用 local ... peer（或 peer map=xxx）
  • [ ] OS 用户与 PG 用户存在且命名一致（或已配置 pg_ident.conf 映射）
  • [ ] CI 用户权限已按最小原则授予
  • [ ] SELECT pg_reload_conf(); 已执行
  • [ ] 测试验证：sudo -u ci_user psql -c 'SELECT 1;' 无需密码
  • [ ] 确认 log_connections = on 以审计 CI 活动

一句话总结：生产环境 CI/Release 通过 SSH 连接数据库服务器后免密执行 psql，正确做法是配置 local + peer 认证，复用 SSH 已建立的 OS 身份信任链，而非使用 trust 或明文密码。
